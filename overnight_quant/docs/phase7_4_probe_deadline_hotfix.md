# Phase 7.4 分钟采样硬截止与审计设计

## 范围

本阶段只加固真实来源资格采样基础设施。它不调整策略权重、阈值、连续三日资格政策或
正式配置，也不增加券商接口、自动交易和证券软件点击能力。所有结果继续保持
`data_ready=false`，`candidates`、`tickets`、`orders` 为空。

## 调度规则

四个目标时点保持为 `14:49:55`、`14:50:05`、`14:50:30` 和 `14:51:05`。

1. 每个分钟请求在独立 Python 子进程内执行，硬截止为 2000ms。
2. 超时后父进程先终止、等待退出，必要时强制杀死；完成清理前主流程不返回。
3. 实际开始时间晚于目标超过 2 秒时记录 `SAMPLE_WINDOW_MISSED`，不得补跑该时点。
4. 单点失败不阻塞后续时点；后续请求仍按各自目标时间启动。
5. mootdx 逐笔请求使用独立可终止子进程和 5000ms 截止，不改变既有归因算法。
6. 两个来源独立运行，严禁跨来源拼接证据。

## mootdx 端点预检

正式四时点之前依次检查候选 TDX 行情端点。端点只有在五只目标股票全部返回时才健康；
选中后四次分钟采样和逐笔采集固定使用同一端点。预检记录端点标识、起止时间、耗时、
覆盖率、来源版本、原始哈希和每次失败的稳定错误码。

预检无法达到 5/5 时返回 `SOURCE_PREFLIGHT_FAILED`。该状态属于可验证的失败关闭证据，
不会继续采样或产生任何策略输出。

## 审计语义

`late_start_count` 统计开始时间晚于目标超过 2 秒的样本；
`deadline_exceeded_count` 统计实际超过硬截止的请求；`missed_sample_count` 统计未补跑的
错失时点；`late_record_count` 仅统计成功返回但超过采样截止的数据记录。网络失败没有
记录时，`late_record_count=0` 是正确结果，但不代表调度成功。

成功请求优先使用子进程内真实 provider 调用起止时间。超时或崩溃时使用父进程掌握的
启动、终止和完成边界，以便审计强制终止是否生效。

## 证据兼容

- 无版本字段：按 v1 原算法验证，保证历史证据哈希不漂移。
- `probe_evidence_schema_version=v2`：哈希额外覆盖预检、逐点调度审计和四项汇总。
- 未知版本：验证失败，不能参与来源资格累计。
- v2 重放必须复制同一证据版本、预检和汇总字段，双重放输出应逐字节一致。

## 验收

自动测试必须证明：40 秒阻塞请求在 2 秒硬截止被终止；返回后不再请求或写文件；连续
两轮互不污染；首点超时不拖延后三点；错失时点不补跑；失败样本仍保留迟到审计；v1
历史哈希稳定；v2 哈希和重放确定；所有异常路径保持研究/影子边界。
